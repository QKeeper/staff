# Инструкции для AI-агентов (AGENTS.md)

Этот документ содержит обязательные правила и стандарты разработки в проекте **staff**.

---

## 1. Обязательная интернационализация (i18n)

В проекте строго запрещено использовать захардкоженные пользовательские строки (plain text) в компонентах. **Любой** текст, отображаемый пользователю, должен проходить через систему локализации `i18next`.

### Правила и требования:

1. **Файлы локализации**:
   - Все ключи и переводы должны синхронно добавляться как минимум в два файла:
     - `src/i18n/locales/ru.json` (Русский язык)
     - `src/i18n/locales/en.json` (Английский язык)
   - Структура JSON должна оставаться консистентной между языками.

2. **Что подлежит переводу**:
   - Заголовки, параграфы, подписи (`<Label>`), названия кнопок.
   - Плейсхолдеры (`placeholder`) в инпутах, текстареях и поисковых строках.
   - Доступность (`aria-label`, `title`, альт-тексты).
   - Опции выпадающих списков (`Select`), подсказки и сообщения об ошибках.

3. **Использование в коде**:
   - Импортируйте хук `useTranslation` из `react-i18next`:
     ```tsx
     import { useTranslation } from "react-i18next";

     const MyComponent = () => {
       const { t } = useTranslation();

       return (
         <div>
           <h2>{t("section.title")}</h2>
           <input placeholder={t("section.inputPlaceholder")} />
         </div>
       );
     };
     ```
   - Группируйте ключи по фичам / виджетам (например: `header`, `sidebar`, `createCommunity`, `feed` и т.д.).

## 2. Форматирование кода через Prettier

Перед сдачей задачи и отчётом пользователю **всегда** необходимо форматировать файлы с помощью Prettier.

### Правила и требования:

1. **Запуск форматирования**:
   - Всегда запускайте форматирование по всему проекту, используя относительный путь `.`:
     ```bash
     pnpm exec prettier --write .
     ```
   - Не форматируйте отдельные конкретные файлы — запускайте проверку и форматирование через `.`.

2. **Соблюдение конфигурации (`.prettierrc`)**:
   - Проект использует `prettier-plugin-tailwindcss` для автоматической сортировки классов Tailwind CSS. Не сортируйте и не форматируйте классы вручную, если это противоречит плагину Prettier.
   - Убедитесь, что отступы, переносы строк и кавычки соответствуют правилам репозитория.

## 3. Валидация перед завершением работы

Перед тем как сообщить о завершении задачи:

1. **Проверка типов TypeScript**:
   ```bash
   pnpm exec tsc --noEmit
   ```
2. **Проверка сборки Vite**:
   ```bash
   pnpm build
   ```

Обе команды должны завершаться без ошибок (exit code 0).

## 4. Создание новых компонентов и UI

При создании новых компонентов и экранов строго запрещено придумывать layout и дизайн «с нуля» на своё усмотрение.

### Правила и требования:

- **Согласование с пользователем**: Перед реализацией нового компонента всегда уточняйте у пользователя, как именно он должен выглядеть:
  - Структура и layout (расположение блоков, сеток, списков).
  - Цветовая палитра и акценты.
  - Состояния элементов (hover, active, disabled, loading).
  - Дополнительные детали визуального оформления.
- Не принимайте самостоятельных решений по внешнему виду без предварительного согласования.

## 5. Оптимистичные обновления интерфейса (Optimistic UI)

Для всех интерактивных элементов с быстрыми действиями пользователя (апвоуты/даунвоуты, лайки, добавление в закладки, переключатели) интерфейс **обязан реагировать мгновенно**, не дожидаясь ответа от сервера:

### Правила и требования:

1. **Мгновенный отклик**: состояние интерфейса (счётчики, активные цвета, иконки) должно изменяться синхронно в момент нажатия.
2. **Отсутствие блокировок**: запрещено блокировать быстрые повторные клики (через `disabled` или флаги загрузки типа `isVoting`), пока запрос выполняется в фоне. Пользователь должен иметь возможность мгновенно отменить действие или переключить выбор.
3. **Синхронизация с сервером (Debounce / LWW)**:
   - При частых кликах отправка запроса на бэкенд должна дебаунситься (например, отправлять финальное выбранное значение с задержкой 250–300 мс) либо версионироваться по идентификатору запроса.
   - Запоздалые ответы сервера не должны перезаписывать свежее локальное состояние пользователя.
4. **Откат при ошибке (Rollback)**: при ошибке сети состояние должно корректно возвращаться к последнему подтвержденному серверному значению.

## 6. Название проекта — Staff (Стафф)

Название текущего проекта — **Staff** (на русском языке — **Стафф**).

### Правила и требования:

1. **Запрет слова «Crates»**: строго запрещено использовать название «Crates» в коде, UI, локализации, комментариях и ответах. Путь к рабочей директории (`/crates`) — это историческое имя папки старого проекта, не имеющего отношения к текущему приложению.
2. **Именование**: в интерфейсе и текстах проект всегда называется:
   - На русском языке: **Стафф** (например: «На Стаффе 4 дня»).
   - На английском языке: **Staff** (например: «On Staff for 4 days»).
